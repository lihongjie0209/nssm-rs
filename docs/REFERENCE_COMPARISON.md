# NSSM reference comparison

This report records direct black-box checks against the pinned NSSM release.
It is a partial report, not the command-by-command release acceptance report.

## Reference and environment

- Source: `ONLYOFFICE/nssm` commit `f28f043161cf6d21c2bf5f923c23b1fbe74d236d`
  (tag `v2.24.1`).
- Reference executable: `nssm_x64.zip` from the
  [v2.24.1 GitHub release](https://github.com/ONLYOFFICE/nssm/releases/tag/v2.24.1).
- Downloaded archive SHA-256: `dd15b0bd3541f954220b8c0622a40294b919dfd0e6635859e733f153ba34bceb`.
- Both binaries were run on the same local Windows host on 2026-10-15.
- Output comparisons normalize trailing whitespace and, for service lists,
  sort service names before comparing.

## Checks completed

| Scenario | Result |
|---|---|
| No arguments | The reference returns status 1. When started without an attached console, the pinned NSSM build attempts its GUI usage dialog; nssm-rs now keeps this CLI-only and writes usage to stderr with status 1. Explicit `help` remains a successful stdout command. |
| `list all ignored` | Both exited 0 and returned the same 331 service names. This confirms the reference behavior of considering only the first optional argument. |
| `list definitely-not-all` | Both exited 0. The host had no NSSM-managed services, so both returned no names. |
| `list` and `list all` | Rechecked both commands against the pinned executable on 2026-10-15; output and exit status matched on this host. |
| Read-only command sweep | `tests/reference_readonly_sweep.ps1` has 86 recognized, non-interactive invocations. All 86 now have matching evidence: the last complete local Windows sweep matched the original 83, and each of the three subsequently added missing-service/unknown-setting cases was separately compared after the fix. Coverage includes native SCM metadata (`Name`, `ImagePath`, `DisplayName`, `ObjectName`, `Description`, `Environment`, `Start`, `Type`, and dependencies) on Spooler and Schedule, all 39 managed-setting queries against the native Spooler service, missing-service `set/reset/unset`, a non-elevating `dump` with a target name, single and multiple-service process reporting, display-name lookup, status/statuscode, and unknown-setting diagnostics. The sweep skips NSSM invocations that can display a GUI dialog and commands that can request elevation. |
| Managed-setting rejection on native services | Querying all 39 managed setting names against Spooler found two compatibility issues: errors needed NSSM's extra carriage return, and `AppExit`/`AppEvents` without a subparameter must report that missing argument before rejecting a native service. nssm-rs now matches those bytes and error precedence; Windows process tests assert the exact stderr bytes for all three cases. |
| `status Spooler` and `statuscode Spooler` | Output and status matched exactly. Both statuscode invocations returned the host's `SERVICE_RUNNING` numeric code (4). |
| `processes Spooler` when the service process cannot be opened | Both exited 0 and emitted no process-tree stdout. Direct local `Start-Process` redirection confirmed exact stderr bytes, including the localized system error and NSSM's trailing blank line. nssm-rs now formats this path with the Windows system message instead of Rust's `(os error N)` suffix; a Windows unit test checks the message shape and line endings. |
| `dump` for equivalent installed services | Compared complete output after normalizing the executable path and service name. Install line, Windows shell escaping, AppParameters, AppDirectory, default AppExit, extra environment, symbolic priority, rotation threshold, Description, DisplayName, ObjectName, Start and Type matched. |
| `dump` for a native SCM service | A Windows integration test creates a disposable service directly through SCM and verifies the dump emits its install command plus native Start and Type settings, without requiring an NSSM `Parameters` registry key. |
| `dump Schedule` when the caller lacks change-config access | The pinned reference requires `SERVICE_CHANGE_CONFIG` even though dump reads configuration. On access denied with exactly one service argument, its CLI requests UAC elevation; nssm-rs now reconstructs that command for elevation. This scenario is excluded from the non-interactive reference sweep because running it can display a Windows consent dialog. Unit coverage checks argument reconstruction, but the UAC round-trip remains unverified. |
| Managed/native setting set/get sweep | Set and read back AppNoConsole, AppPriority, AppRestartDelay, AppThrottle, AppRotateBytes, AppAffinity, AppExit Default, AppEnvironmentExtra, AppParameters, AppDirectory, Description, DisplayName, ObjectName, Start and Type on paired temporary services. Exit codes and normalized output matched for every case. |
| All 28 managed DWORD settings | Paired temporary services matched on set/get/reset, configured values, reset defaults, and exit codes for all 28 Windows DWORD settings. |
| String and hook setting set/get/reset sweep | AppParameters, AppDirectory, AppStdin, AppStdout, AppStderr, AppAffinity, AppEnvironment, AppEnvironmentExtra, AppExit and AppEvents matched in values and reset defaults. On this host, resetting AppParameters or AppDirectory with the pinned NSSM binary terminated it with Windows status `0xC0000374` (heap corruption); nssm-rs completes the same reset successfully. This reference crash is recorded as an intentional safety difference. |
| `get Spooler Start` | Both exited 0 and returned the same startup type. |
| `get Spooler Type` | Both exited 0 and returned the same service type. |
| `get Schedule Type` | The pinned NSSM returns `SERVICE_WIN32_SHARE_PROCESS`; nssm-rs initially returned `SERVICE_TYPE_32`. Native type formatting now matches all six NSSM service-type names, with unit coverage and a Windows SCM assertion for a shared-process service. |
| Native service lookup by display name | `get "Task Scheduler" Start` and `get "Task Scheduler" Name` match the pinned reference byte-for-byte on the local Windows host. The integration test verifies display-name resolution and that `Name` returns the canonical key `Schedule`. |
| `get Spooler DisplayName` | Both exited 0 and returned the same display name. |
| `get Spooler ObjectName` | Both exited 0 and returned the same account name. |
| `get Schedule AppRotateBytes` | Both exited 1 with empty stdout and the same diagnostic: `Parameter "AppRotateBytes" is only valid for services managed by NSSM!`. nssm-rs now identifies native services before looking up managed settings; a Windows integration regression test covers this path. |
| `get Spooler DependOnService` | Both returned `RPCSS` and `http` in the same order. The reference emits `CR CR LF` between items and CRLF at the end; nssm-rs now reproduces those exact line-ending bytes for all CLI multi-string reads. |
| `set/get AppAffinity` | Directly compared on the same Windows host: `0-1` reads back as `0,1`; `0,1,2` reads back as `0-2`; `Default`, `All`, and `*` each read back as `All`. nssm-rs matches the reference output and exit status for these values. |
| `set/get AppAffinity 0-64` | Both binaries accept this range and read it back as `0-63` on the pinned x64 reference build. The reference parser checks the range start but not its end; nssm-rs reproduces the observed x64 result with explicit wrapping mask logic. A standalone CPU index `64` is rejected by both; both return exit code 6 and preserve the prior setting. |
| `get <new-service> AppExit Default` immediately after install / after first start | Both return `Restart`. NSSM creates the `AppExit` default during install; nssm-rs now does the same. A missing default inside an existing malformed key remains handled deterministically as `Restart` rather than NSSM's uninitialized control character. |
| `get Spooler Description` | Direct `cmd.exe` file redirection showed identical raw bytes, including `?` replacement and CRLF. In PowerShell's native-command pipeline, both emit the same localized text. The reference selects UTF-8 when launched from an existing console; nssm-rs now mirrors that mode, writes UTF-16 to console handles, and uses the MSVC CRT's code-page-1252 no-best-fit conversion when launched without an existing console. A Windows lifecycle integration assertion checks redirected bytes. |
| `statuscode` for a missing service | Both exited 0, matching NSSM's documented failure sentinel. On the local Chinese Windows host, raw stdout and stderr bytes now match exactly, including NSSM's localized system error replacement and CRT line endings. |
| Missing-service lookup for `status`, `start`, `stop`, `restart`, `pause`, `continue`, `rotate`, `get`, `set`, `reset`, and `statuscode` | Directly compared on the local Windows host: exit status and raw stdout/stderr bytes match for each command, including the NSSM message resource line endings and localized system error. The Windows integration test covers the status and statuscode message shape. |
| Unknown setting on a missing service | Direct reference comparisons for `get`, `set`, and `reset` showed that invalid-setting diagnostics take precedence over the missing-service lookup error. nssm-rs now follows that order; a Windows CLI integration test checks all three commands, exit status, and diagnostic class. |
| Missing-service `remove` | NSSM checks administrator status and requests elevation before looking up the service. nssm-rs now follows that order and emits the same administrator-required notice before elevation; the local elevated integration suite verifies exit code 3 once running in the administrator context. |
| `processes` for missing and multiple services | Both return exit code 1 and emit the same raw stderr bytes on the local Windows host. A two-service comparison confirms that the missing-service `EnumServicesStatus()` diagnostic precedes the following service's process-open diagnostic, as it does in the reference. The Windows integration regression covers missing-service exit code and diagnostic shape. |
| Setting operation failures | The pinned source returns 5 when a known setting cannot be read and 6 when a known setting cannot be changed; unknown parameters return 1. nssm-rs maps these paths accordingly. The SCM lifecycle integration test checks the missing `AppExit` read (5), invalid `Start` value (6), and unknown setting (1). |
| `continue` during restart throttling | The reference writes Application event 1035 (`RESET_THROTTLE`) with the service name when Continue resets the throttle. nssm-rs now reports the same event from its SCM control handler; the real service integration test checks the event record. |
| SCM control diagnostics | The reference reports event 1040 (`SERVICE_CONTROL_HANDLED`) for handled START, STOP and CONTINUE controls and event 1041 (`SERVICE_CONTROL_NOT_HANDLED`) for unsupported PAUSE controls. nssm-rs now logs the same service/control insertion values; Windows SCM integration asserts START, STOP and PAUSE records. |
| Restart throttle event logging | The reference reports event 1034 (`THROTTLED`) with the configured threshold and retry delay, or event 1072 (`RESTART_DELAY`) when the configured restart delay exceeds exponential backoff. nssm-rs now emits both forms; SCM integration scenarios assert the event IDs and insertion values. |
| Failed application restart launch | Reference `service.cpp` logs warning event 1007 with executable and service name, then waits 30 seconds and retries. The local elevated Windows SCM suite passed the scenario that removes the executable during its configured restart delay and verifies event 1007. This validates nssm-rs behavior against the source contract; a direct side-by-side reference run of this failure scenario remains outstanding. |
| Standard-stream file creation failure | Reference `io.cpp` logs event 1049 with the path and localized system error; `service.cpp` then logs 1051 and 1006 with service name and service-specific exit code 4. The local elevated Windows SCM suite passed the missing-directory scenario and verified all three records. Exact localized message parity remains part of the broader reference comparison. |
| Identical stdout and stderr paths | Reference `io.cpp` opens the path once and duplicates the stdout handle for stderr, including case-insensitive path matching. nssm-rs now duplicates the file handle and honors stdout's file settings for both streams. When timestamping or online rotation uses a logger pipe, stderr keeps the duplicated file handle as in NSSM. The local elevated Windows SCM suite passed the integration case that sets conflicting truncation options and confirms stdout's setting wins. |
| Hook lookup and process-creation failures | Reference `hook.cpp` logs event 1081 when a configured hook cannot be read and event 1080 when its command cannot be created. The elevated Windows SCM suite verifies event 1080 for a missing Start/Pre executable and event 1081 after denying SYSTEM read access to the isolated Start hook registry key; both failures leave service startup running. |
| Missing application arguments and working directory | Reference `registry.cpp` logs warning events 1029 and 1030 when `AppParameters` or `AppDirectory` is absent. The local elevated Windows SCM suite passed the scenario checking both event IDs, insertion values, fallback directory, and child lifecycle. |
| Log rotation failure | Reference `io.cpp` logs event 1063 with service, active path, failed operation, rotation target and localized error. The local elevated Windows SCM suite passed the forced startup rename collision, verified event 1063 insertion values, and confirmed the child still launches. |
| Service control handler registration failure | Reference `service.cpp` logs event 1005 with the Windows error if registering the SCM handler fails. A Windows unit test invokes the real service entry point outside an SCM dispatcher, causing `RegisterServiceCtrlHandlerExW` to fail and verifying event 1005 in the Application log. |
| Process tree enumeration diagnostics | Reference `process.cpp` logs events 1024, 1025, 1026 and 1044 for process snapshot, enumeration, descendant handle and process-time failures. Windows tests deterministically inject each OS API failure through the production traversal path and verify the corresponding Application log records. Event 1050 is verified by injecting a duplicate-handle failure through the shared stdio error path. |
| Successful log rotation | The reference reports event 1077 (`ROTATED`) with the service name, active log path, and backup path. nssm-rs now reports the same event for startup and live rotations; a Windows SCM integration assertion checks the event's three insertion values. |
| `version` | Both commands succeed, but each reports its own binary identity and build metadata. |
